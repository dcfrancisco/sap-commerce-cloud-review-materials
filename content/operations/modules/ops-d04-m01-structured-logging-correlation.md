# OPS-D04-M01: Structured Logging and Correlation

## Purpose and scope

Production diagnosis begins with a trustworthy record of what happened. This chapter teaches an SAP Commerce Cloud operations engineer to design, search, preserve, and interpret structured log evidence across a commerce request, a background task, a deployment, and a dependency. It deliberately separates three things that are often conflated: behavior documented for SAP Commerce Cloud public cloud; engineering practices that apply to distributed Java systems; and behavior generated by this academy's deterministic simulation.

The examples use the SAP Commerce Cloud public-cloud 2211 documentation scope available at the time of this release. A target environment must still be checked for its update level, enabled observability services, retention, permissions, and current Cloud Portal interface. A field name shown in an example is not automatically a universal SAP contract. The local academy simulation is not the SAP Commerce runtime and cannot validate a customer's subscription configuration.

## Learning outcomes

By the end of this module, a learner can:

1. Explain the difference between application, access, deployment, Catalina, audit, and business-event records.
2. Define a privacy-safe structured event with a stable correlation identifier, event time, source, operation, outcome, and versioned schema.
3. Build a bounded investigation in OpenSearch using an environment, time window, platform aspect, log origin, and correlation value.
4. Distinguish a request identifier from a business identifier and avoid treating timestamp proximity as causal proof.
5. Reconstruct a cross-signal timeline without losing the original records or silently rewriting evidence.
6. Design negative-path tests for missing identifiers, duplicate events, clock skew, redacted fields, malformed payloads, and partial failures.
7. Explain when an observation is a verified SAP fact, a version-dependent fact, an independent engineering recommendation, a simulation rule, or an unresolved assumption.

## Prerequisites

Learners should understand HTTP requests, Java logging at a high level, basic JSON, SQL-like filtering, and the difference between a customer-owned extension and a managed service. Familiarity with SAP Commerce extensions, OCC requests, CronJobs, catalog synchronization, and deployment records is helpful. The chapter does not require access to a live SAP Commerce Cloud subscription; the exercises include a deterministic evidence set. A live runtime is required to validate actual field mappings, retention, permissions, and query syntax for a selected release.

## Authority and responsibility boundaries

SAP's public-cloud documentation describes OpenSearch as the logging management plugin used by Cloud Portal and explains that logs can be accessed from an environment's Monitoring panel. It also distinguishes shared Global, private, and custom tenants [RS-SAP-ENV-LOGS]. The same documentation family describes access and Catalina logs and gives filters based on the platform aspect and `logs.origin` [RS-SAP-ENV-LOGS]. The 2211 platform logging reference discusses Log4j2, SLF4J, JSON logs, JDBC logging, and access logging [RS-SAP-PLATFORM-LOGGING]. Those are platform facts within the cited documentation scope.

The customer is responsible for the logging behavior introduced by its custom code: useful event names, safe fields, exception classification, and avoiding personal or payment data. The customer does not thereby gain host access, unrestricted database access, or permission to change managed logging infrastructure. A log query, export, retention change, or support escalation must be performed only through the capabilities and roles available to the target subscription. If the evidence suggests a managed service problem, preserve the time window, environment, build, request identifiers, query, and impact summary before escalating. Do not “fix” a managed platform condition by deleting evidence or repeatedly restarting components.

## What makes a log event useful

A useful event answers five questions: when did it happen, where did it happen, what operation was attempted, what was the outcome, and how can another record be connected to it? A practical event envelope is:

```json
{
  "schemaVersion": "commerce.operation.v1",
  "eventTime": "2026-10-16T03:12:14.221Z",
  "environment": "staging",
  "platformAspect": "accstorefront",
  "service": "checkout-facade",
  "operation": "placeOrder",
  "outcome": "failed",
  "correlationId": "c-7a3f",
  "traceId": "t-81b2",
  "businessReference": "order-attempt-9421",
  "durationMs": 1834,
  "errorClass": "InventoryReservationTimeout",
  "version": "release-2026.10.16.3"
}
```

`correlationId` connects records within one diagnostic journey. `traceId` may connect distributed spans when the supported tracing solution supplies it. A business reference identifies a domain operation and must be protected more carefully than a random request identifier. It is often safer to log a token or hash than an email address, payment token, cart contents, address, or full authorization header. If a support workflow requires a real order or customer reference, document the access control and minimization rule.

Event time should be UTC and should be recorded at the producer. In a distributed system, ingestion time and event time can differ. Keep both when the platform exposes both. Never sort only by a displayed dashboard time and infer that the last visible event caused the first visible error. Clock skew, batching, retries, asynchronous delivery, and log ingestion delay can reorder observations. A timeline should preserve the source timestamp, ingestion timestamp if available, source record identifier, and the analyst's confidence.

Use stable low-cardinality dimensions for dashboards: environment, platform aspect, service, operation, outcome, error class, and release. Avoid placing arbitrary customer identifiers, complete URLs, query strings, item payloads, or exception messages into metric labels. Logs can contain more diagnostic detail than metrics, but logs still require a retention and privacy policy. A structured event is not safe merely because it is JSON.

## SAP Commerce-specific signals

The public-cloud documentation identifies multiple log families. Access logs help establish inbound request volume and status behavior. Catalina logs help investigate Tomcat startup and internal Tomcat behavior. Application logs contain extension and platform messages. Deployment records establish what changed and when. Audit logging is a separate accountability mechanism: SAP documents that selected security-relevant events in Backoffice and Administration Console are forwarded to the logging tool, and that database operations, authentication, and CronJob events are audited across applications [RS-SAP-HELP-AUDIT]. Audit records should not be treated as a replacement for application diagnostics or as permission to log sensitive payloads.

For a checkout investigation, begin with the customer impact and then associate the request path. A safe evidence sequence is:

1. Define the UTC incident window from the first known business symptom.
2. Identify the environment, release/build, and platform aspect involved.
3. Compare access volume, status codes, and tail latency with the application records.
4. Follow the correlation or trace identifier into checkout, inventory, payment, and persistence records where those records are legitimately available.
5. Compare deployment and configuration changes in the same window.
6. Preserve representative success and failure samples, not only the loudest exception.
7. Validate whether the customer-visible business outcome is known, unknown, duplicated, or merely delayed.

For a background operation, include the job or process identifier, trigger type, execution start/end, page or batch checkpoint, item count, retry number, and cancellation result. A CronJob record proves that an execution was scheduled or attempted; it does not prove that all business side effects succeeded. A catalog or order process may involve asynchronous steps. Use business reconciliation evidence before declaring recovery.

## OpenSearch investigation method

OpenSearch is the investigation interface described by the SAP Help source for environment logs. The exact dashboard query language, index pattern, tenant permissions, and field availability must be verified in the target environment. The following query shapes are teaching examples, not claims of a universal field schema:

```text
environment = "staging"
AND eventTime >= "2026-10-16T03:00:00Z"
AND eventTime <  "2026-10-16T03:20:00Z"
AND platformAspect = "accstorefront"
AND correlationId = "c-7a3f"
```

SAP's documented access-log filter uses the platform aspect and `logs.origin:access-log`; the documented Catalina examples use `logs.origin:catalina` or an equivalent structured filter [RS-SAP-ENV-LOGS]. Use the product's documented query form rather than copying a syntax from an unrelated OpenSearch installation. Save the query, time zone, tenant, selected index pattern, and result count in the investigation record. If the result count changes because of late ingestion, record the observation time and rerun rather than overwriting the first result.

Start narrow. A broad query over a long period creates noise, increases the chance of accidental sensitive-data exposure, and makes causal reasoning harder. Expand one dimension at a time: time, aspect, origin, service, correlation, error class, then adjacent signals. Add a control query for known-good traffic. If a filter returns zero records, distinguish “no event exists” from “the field is not mapped,” “the tenant cannot see it,” “the retention window expired,” and “the event was never emitted.” Each explanation leads to a different next action.

Use representative sampling. Preserve the first failure, one failure during the peak, a successful request in the same period, and a post-mitigation request. Record the reason for selecting each sample. For high-volume events, aggregate only after retaining enough raw references to reproduce the conclusion. Do not paste complete customer payloads into an assessment answer or a support ticket.

## Correlation is not causation

Correlation identifiers make a causal investigation possible; they do not make the conclusion automatic. A request can call multiple services, a retry can create multiple records, and a background job can contend for shared resources without sharing the same request ID. Use a relationship table:

| Evidence | What it supports | What it does not prove |
|---|---|---|
| Same correlation ID | Records belong to one request journey | The earliest record caused every later record |
| Same minute | Events overlap in time | One workload caused the other |
| Deployment before errors | A change is a plausible contributor | The deployment is the root cause |
| Exception repeats | A failure mode is recurring | The exception is the first cause |
| Recovery after containment | The mitigation is compatible with recovery | The system is safe to close |

The stronger conclusion combines event chronology, service flow, resource evidence, change history, and business outcome. Dynatrace documentation for SAP Commerce describes services, transactions, databases, dependencies, and process relationships as investigation surfaces [RS-SAP-DYNATRACE]. That capability can connect a request to downstream latency, but the learner must still validate the relationship and version-specific availability. An independent recommendation in this manual is to write the causal sentence with evidence and confidence: “The export workload is the leading contributor because pool wait rose before checkout tail latency, the trace shows checkout waiting on the same pool, and stopping the export reduced both; payment reconciliation remains open.”

## Failure cases and troubleshooting walkthrough

### Missing correlation identifier

Symptom: an OCC failure record contains a timestamp and status but no correlation ID. First check whether the identifier is in a neighboring access record, response header, trace context, or gateway record. If it cannot be recovered, label the evidence as uncorrelated and use the smallest reliable window. Do not manufacture a value. Create a corrective action for the extension or boundary that dropped context, and add a test that asserts propagation through success and failure paths.

### Duplicate or retried events

Symptom: two “order submitted” messages appear for one customer attempt. Compare event IDs, idempotency keys, business references, retry counters, and downstream order state. A duplicate log line is not necessarily a duplicate side effect, and one side effect can have several legitimate log records. The investigation must separate event duplication, message redelivery, and business duplication.

### Sensitive data exposure

Symptom: a debug exception contains an address, authorization header, or payment detail. Stop further propagation through the supported application configuration, preserve only the minimum evidence required for incident response, restrict access, and escalate under the organization's security process. Do not copy the payload into a public issue, assessment answer, or AI tutor context. Add redaction tests and verify that the fix does not remove the error class or correlation context needed for diagnosis.

### Log ingestion delay

Symptom: the application is healthy but the dashboard appears empty. Compare an application-side timestamp or synthetic transaction with the log ingestion timestamp, check the selected tenant and index pattern, and record retention limitations. Do not declare that no request occurred solely from an empty search result. A delayed logging pipeline is itself an observability incident and should have an owner and SLO.

### Contradictory records

Symptom: an application record says “success” while the order state is still pending. Treat the records as different layers of truth. Confirm transaction commit timing, asynchronous process state, external response, and reconciliation status. Use “technical request returned success” rather than “order completed” until the business state is independently verified.

## Guided practice: reconstruct a checkout trace

Objective: create an evidence-preserving timeline from a synthetic log bundle.

Initial state: the local scenario provides access records, application records, a deployment event, a database-pool observation, and three ambiguous payment outcomes. The records are clearly labeled simulated. No actual SAP Commerce or OpenSearch endpoint is used.

Procedure:

1. Start a fresh `OPS-INC-002` session and record the scenario ID and session ID.
2. Investigate service SLI, change events, service flow, and transaction integrity.
3. Build a table with event time, ingestion or observation time, source, correlation/business reference, outcome, and confidence.
4. Mark the leading hypothesis and at least two rejected alternatives.
5. Identify which fields are safe to retain in a support package and which must be redacted.
6. Pause the custom export only after recording the pre-action evidence.
7. Validate technical recovery and separately identify the payment reconciliation work.

Acceptance criteria: the timeline has at least one control success and one failure; the deployment is not declared causal from time proximity alone; the custom workload and checkout evidence are linked through a defensible resource path; ambiguous payment state is not silently marked complete; every simulated action is recorded; and the learner states the boundary between this simulation and a live SAP environment.

Failure cases include selecting a broad query before establishing the window, using a customer email as a correlation key, treating a log exception as a completed order state, and recommending direct database session termination. The reference solution is to preserve identifiers, align windows, use cross-signal evidence, contain the customer-owned workload through a supported simulation action, verify technical recovery, and open reconciliation for business ambiguity.

## Independent practice

Design a logging contract for a custom catalog synchronization extension. Define event names for start, batch completion, item rejection, retry, cancellation, and final outcome. Include schema version, catalog and catalog-version tokens, correlation ID, batch checkpoint, source release, duration, count, and error class. State which fields must be omitted or hashed. Provide unit tests for serialization and redaction, an integration test for persistence of checkpoints on the target SAP Commerce update line, an API or log-contract test for propagation through the job trigger, and a failure injection test for interruption after a batch commit but before the next checkpoint. Record which tests ran in simulation and which require the platform runtime.

The exercise is not complete when the Java code compiles. It is complete when success, rejection, retry, cancellation, duplicate execution, and partial-failure paths have assertions, evidence is retained, and the learner can explain how an operator distinguishes a missing event from a query or retention problem.

## Diagnostic exercise

You receive the following claims: “Checkout failed at 03:12 because the deployment happened at 03:11,” “the dashboard has no errors so the issue is not in Commerce,” and “the same order ID appears twice, so the customer was charged twice.” Review each claim. For each, identify the unsupported inference, request the next evidence, state a safer hypothesis, and define a verification check. A high-quality response will request release/build records, access and application logs, correlation or trace context, dependency and transaction evidence, and an authoritative payment/order reconciliation rather than accepting any claim as fact.

## Tutor behavior

Athena's tutor may explain the difference between event time and ingestion time, ask which hypothesis a query would falsify, or point to the available evidence. In tutoring mode it can provide a bounded hint grounded in this chapter and the cited sources. In examination mode it can clarify the meaning of a field and reveal requested evidence, but it must not reveal the reference cause, preferred recovery, or answer key. Semantic feedback may comment on clarity and missing structure; deterministic evidence and safety constraints control the score.

## Assessment and competency evidence

The module assesses OPS-OBS-004 through evidence correlation and OPS-OBS-005 through observability strategy. Knowledge items are scored independently from practical reasoning. A correct answer must identify the boundary of the evidence; repeating words such as “correlation ID,” “OpenSearch,” or “root cause” without a defensible chain does not pass. The incident engine records investigation IDs, query/action order, rejected alternatives, safety decisions, verification, and unresolved uncertainty. A learner who can name a log field but cannot protect privacy, preserve evidence, or verify business state does not receive independent-production mastery.

## Testing requirements

At minimum, implement tests for: valid event serialization; missing and duplicate correlation IDs; UTC and malformed timestamps; redaction of credentials and payment data; unknown event schema versions; retry counters; clock-skew ordering; empty-query handling; tenant or retention ambiguity; contradictory technical and business outcomes; and preservation of original records after timeline annotation. For a SAP Commerce runtime, add version-appropriate platform integration tests around the actual extension logger, CronJob/process execution, transaction boundary, and log forwarding path. Ordinary Python or Spring unit tests in this repository do not prove those platform behaviors.

## Security and privacy

Logs are operational data and may contain personal, commercial, or security-sensitive information. Apply least privilege to the logging tenant and support package. Avoid access tokens, passwords, session cookies, full payment data, and unbounded request payloads. Use synthetic identifiers in training. Redaction must be tested before and after exception handling, because a formatter that protects the normal path may still leak through a nested exception or debug statement. Audit access to sensitive diagnostic records where the target platform supports it. Do not submit learner-provided logs to an external AI provider without explicit policy, minimization, and provider controls.

## Senior engineering insights

Observability is a product capability, not a pile of strings. The best event schema makes safe diagnosis easier while limiting the damage of disclosure. Correlation should be propagated deliberately across synchronous and asynchronous boundaries; it should not be confused with a business idempotency key. Logging must be designed with operational cost: high-cardinality fields, excessive stack traces, and unbounded payloads can increase storage and query cost and still fail to explain business impact. A useful alert should lead an operator to the smallest evidence bundle that can distinguish likely causes.

Treat missing evidence as a state, not an invitation to invent. “Unknown because the tenant has no field” is different from “known false.” Treat a simulation record as a teaching fixture, not a promise that Cloud Portal, OpenSearch, Dynatrace, or a particular update release exposes the same interface. Record the version, subscription, query, and observation date for every production conclusion.

## Summary

Structured logs make events searchable; correlation makes paths reconstructable; neither replaces reasoning. A defensible SAP Commerce Cloud investigation starts with business impact, bounds the time and environment, uses documented logging surfaces, follows identifiers across application and dependency evidence, preserves privacy, and verifies technical and business recovery independently. The local incident simulator demonstrates this reasoning and records competency evidence, but only the target SAP Commerce update line can validate platform-specific logging, integration, retention, and permission behavior.
